# Cosmos Policy integration

Everything needed to put this external model back on a machine that does not have it.
Nothing here is imported by `a3_dual_arm_sim` at runtime -- the adapter runs in the
model's own interpreter, reached over the bridge protocol.

| File | What it is |
| --- | --- |
| `adapter_cosmos_policy_aloha.py` | The model-side adapter: A3 request in, ALOHA action chunk out. Kept in sync with the live copy in the model checkout (compare with `sha256sum`). |
| `fetch_hf_file.py` | Parallel, resumable download of one large file from the Hub. Written because a single stream runs at 3.4 MB/s here and the T5-XXL encoder is 45 GB. |
| `wire_hf_cache.py` | Puts a downloaded file into the Hugging Face cache in the layout the library expects, verifying it against the recorded SHA-256. |

The manifest that drives it is `configs/policies/cosmos_policy_aloha.yaml`.
Background and the runtime findings are in `docs/external-policy-bridge.md`
(section 7.4 covers the language conditioning in detail).

## Why the pieces are where they are

`policy check` audits the manifest without installing anything, so this directory is
about rebuilding: the environment, the weights, and the text-embedding cache.

## 1. Environment

```bash
git clone https://gh-proxy.com/https://github.com/NVlabs/cosmos-policy.git /root/autodl-tmp/cosmos-policy
cd /root/autodl-tmp/cosmos-policy
uv venv --python 3.10 .venv
uv sync --extra cu128
```

Three things about that, all learned the hard way:

- **`gh-proxy.com` is the fast GitHub proxy here** (6-11 MB/s). `ghfast.top` and
  `ghproxy.net` measure 25-30 KB/s, a factor of 400.
- **`cu128` is mandatory.** The RTX 5090 is sm_120, and the cu121/cu124/cu126 torch
  wheels contain no sm_120 kernels -- they fail with "no kernel image is available".
  The `cu128` extra is already declared in the repo's own `pyproject.toml`.
- **Do not go looking for `flash-attn`, `natten` or `transformer-engine` on PyPI or
  in NVIDIA's index.** The project declares a private index for exactly these:

  ```
  https://nvidia-cosmos.github.io/cosmos-dependencies/v1.2.0/cu128_torch27/simple/
  ```

  It carries prebuilt wheels for all three, and the fused kernels execute on sm_120.
  Reading the project's own `pyproject.toml` first saved a half-hour source build.
  The general lesson: check a project's private index before compiling anything.

## 2. Weights

| Repo | Size | Gated? | Needed |
| --- | --- | --- | --- |
| `nvidia/Cosmos-Policy-ALOHA-Predict2-2B` | 3.9 GB | no | yes -- the policy |
| `nvidia/Cosmos-Predict2-2B-Video2World` | 4.2 GB | **yes** | yes -- the base DiT and the Wan2.1 VAE, pulled by the loader even when the fine-tuned weights are present |
| `google-t5/t5-11b` | 45.23 GB | no | only to use prompt strings outside the shipped cache -- see section 4 |

The gated one needs a token with access granted. `HF_HOME` and `HF_ENDPOINT` are set in
the manifest rather than in the adapter, because they are facts about this machine:
hub access is blocked here and `hf-mirror.com` is not.

## 3. The task-label cache, and what it is not

`aloha_t5_embeddings.pkl` next to the checkpoint maps *instruction string* to a
precomputed T5-XXL embedding. It ships with six entries.

**It is a cache, not a whitelist.** `get_t5_embedding_from_cache`
(`cosmos_policy/experiments/robot/cosmos_utils.py`) computes the embedding and writes
it back when a string is missing. So an arbitrary instruction is a supported input --
it just costs an encoder.

Two consequences worth knowing before reading the adapter:

- The adapter's substitution of an unknown string is a **cost guard**, not a
  correctness one. It exists because building T5-XXL inside a rollout is a 45 GB
  surprise, not because the model would reject the string. `allow_t5_encode: true`
  in the manifest turns the guard off deliberately.
- The dtype of an entry records how it got in. The five labels generated by
  `cosmos_policy/datasets/save_aloha_t5_text_embeddings.py` are `bfloat16`; anything
  added by the auto-write-back path is `float32`, because that path does not cast.
  A `float32` entry in an otherwise `bfloat16` cache was written at inference time.

## 4. Using a custom instruction

Only viable now that there is disk for the encoder. Both scripts are needed:

```bash
# 1. Fetch the encoder (~45 GB, ~65 min at 11 MB/s with 12 workers)
python integrations/cosmos_policy/fetch_hf_file.py \
    --repo google-t5/t5-11b --file pytorch_model.bin \
    --output /root/autodl-tmp/t5-download/pytorch_model.bin \
    --workers 12

# 2. Put it where `from_pretrained("google-t5/t5-11b")` will find it.
#    Exporting HF_HOME first is essential: the encoder is resolved by Hub id against
#    the cache, not by any local path, so a file in a download directory is invisible.
export HF_HOME=/root/autodl-tmp/hf
python integrations/cosmos_policy/wire_hf_cache.py \
    --weights /root/autodl-tmp/t5-download/pytorch_model.bin \
    --expect-sha256 <the sha256 the Hub records>

# 3. Back up the cache before the first write-back. It is a single file with no
#    second copy anywhere.
cp /root/autodl-tmp/models/Cosmos-Policy-ALOHA-Predict2-2B/aloha_t5_embeddings.pkl{,.orig}

# 4. Run once with the guard off. The first request encodes and writes back; every
#    later one is a cache hit.
A3_POLICY_MANIFEST=<manifest with allow_t5_encode=true> ...
```

Measured on this machine: first inference 87.7 s (encoder load plus one encode),
second 24.1 s, and the pkl grows from 7.3 MB to 9.4 MB with a seventh entry.

**The encoder choice is not free.** The paper states the conditioning is T5-XXL
embeddings, and T5-XXL *is* `t5-11b`. Handing the model an embedding from a different
text tower -- a Chinese T5, CLIP, Qwen -- produces no error and no useful conditioning:
the cross-attention does its dot product against a geometry it has never seen. Passing
an array is a way to *transmit* a T5-XXL embedding, not a way to *replace* the encoder.

**Skipping the download.** To use a custom instruction without 45 GB on this machine,
encode it elsewhere with
`cosmos_policy.datasets.t5_embedding_utils.generate_t5_embeddings([...])`, copy back
the resulting ~2 MB pkl, and point `--config t5_embeddings=<path>` at it. The write-back
means one encode is enough; it does not have to be repeated.

## 5. Disk

| Item | Size |
| --- | --- |
| `.venv` | 12 GB |
| Checkout | 23 MB |
| Policy + base weights | 8 GB |
| T5-XXL (optional) | 45 GB |

After a custom instruction has been cached, the 45 GB encoder is only needed again to
encode a *new* string. An encoder-only extraction is 4.86 B parameters (`19.4 GB` in
fp32, `9.7 GB` in bf16) if that trade is worth making.
